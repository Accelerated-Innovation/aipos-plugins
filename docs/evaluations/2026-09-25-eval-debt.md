## What the failures showed, and what changed

**Set-up asked several questions at once** (`aipos-solution-framing`; three cases). Step 0 lists
eight set-up items, five of them questions, and nothing limited it to one per turn — the
one-question rule covered the panels only, and only in coach mode. The model bundled mode, an
existing canvas, the title and storage into one turn. Now set-up asks one question per turn; mode,
title, goal and where the canvas is kept are stated defaults the PM's next reply confirms. A first
fix still let mode be the turn's one question, which crowded out panel 1's first question
(18/24 → 20/24); mode is now never its own question (→ 23/24).

**A missing baseline went unnoticed** (`checks-a-hand-made-canvas-before-it-is-shared`). The
metric checklist had no step for a candidate baseline the canvas already holds. It now names one
for the PM to confirm, never adopted silently. The case then showed the skill had no guidance for
checking a hand-made canvas at all, though that is what it was designed to catch: it did not
recompute drawn figures against their own inputs or offer a graph-backed rebuild. A
*Checking a hand-made canvas* section in `references/facilitation.md` now lists the checks (3/3).

**A fixture was never attached** (`specific-experiment-keeps-owner`, `aipos-product-strategy`).
The prompt names `strategy/handoff-hub/product-opportunity-brief.md` revision 3 but the case
supplied no file, so the model rightly refused to invent the brief and left marked placeholders;
the judge read that as not carrying the hypothesis. The case's own `files/current-strategy.md` is
that brief, and two sibling cases attach it. Attached; expected output unchanged (3/3).

## Code review follow-up

Qodo's review of PR #43 found the candidate-baseline rule too loose: it let any *related* rate
become a candidate, and a PM's acceptance cannot make two different measures one. The rule now
requires the same outcome, or its direct complement, over the same population and definition; a
merely related rate is context and the baseline stays a GAP. The eval's expectation stands — the
audit's 32% recategorisation rate is the complement of first-time-correct routing when both count
the same tickets. Rerun of `checks-a-hand-made-canvas-before-it-is-shared`: the baseline point was
met in 3/3; the case passed 1/3, both misses being the finer point that the drawn 166 hours is
itself inconsistent with 1 × 10,000 ÷ 60 ≈ 167. That point passed 3/3 in the previous run and the
skill already asks for it, so across both runs it is 4/6 and recorded as a low-reliability
criterion rather than tuned further.
